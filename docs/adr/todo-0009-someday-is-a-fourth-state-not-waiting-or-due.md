# ADR todo-0009: いつかは第4の状態。待ちへ寄せず、期限も流用しない

## 背景

「いまは着手順に置かないが、いつか再開したい」タスクの置き場が無かった。既存の3状態はどれも意味が違う。

`waiting` は `--to` が必須で、「相手にボールを渡した」ことが前提になっている。相手がいないのに待ちへ入れると、5日で琥珀・10日で赤の催促表示が誤作動し、「誰も渡していないのに催促されている」状態になる。`Task.StalledFor` も `HandedOn` を起点に数えるので、相手のいないタスクにはそもそも意味を持たせられない。

`open` に置いたまま `Due` を遠くに設定する案も考えたが、`Due` は「その日までにやる」という約束で、超過すれば赤帯が付く。棚上げは約束ではなく「この日までは見なくていい」という逆方向の意味で、同じ場所に置くと超過表示が誤作動する。

## 決定

**状態を1つ増やす。** `open` / `waiting` / `someday` / `done` の4つ。`someday` は着手順から抜けており、`Order` の通し番号は 着手順 → 待ち → いつか → 完了 の順で振り直す。

**日付は `Until` という新しいフィールドで持ち、`Due` とは分離する。** `Due` は「約束した期限」、`Until` は「この日までは見なくていい」で、意味が逆なので同じフィールドに載せない。超過の色分けも共有しない。API は `until_reached`（`Until` が今日以前）を計算して返し、画面と CLI は再計算しない（既存の `due_label` / `due_class` と同じ方針）。

**遷移**: `open → someday`（shelve、`Focused` を false にする）、`waiting → someday` も許可（相手待ちのまま寝かせたい場合がある）、`someday → open`（既存の `resume` を再利用し、着手順の末尾へ戻し `Until` をクリア）、`someday → done`（棚上げ中に片付いた場合）。

**理由の質問対象にしない。** `NeedsReason` の対象は変えない。棚上げは並べ替えでも削除でもなく、質問キューに乗せる理由がない。

**undo は既存の仕組みをそのまま使う。** `shelved` イベントに変更前の `Task` を丸ごと `Snapshot` として持たせ（`removed` イベントと同じ形）、逆操作はスナップショットをそのまま書き戻す。新しい undo の仕組みは足していない。

## 捨てた案

- **`waiting` へ寄せ、`--to` を空で許す**: 相手がいないのに経過日数の催促が発火する。「誰に渡したか」を意味のないまま持たせることになる
- **`open` のまま `Due` を遠くに設定する**: `Due` は超過すれば赤帯になる約束の日付で、「見なくていい日」という逆方向の意味を同じ列に混ぜると表示が壊れる
- **着手順の最下段に置く**: 状態を増やさずに済むが、`Order` を持つ他の着手順タスクと同じ扱いになり、並べ替え・スコープ判定・理由質問の対象から外す条件分岐が state 以外の場所（順序・フラグ）に散らばる。状態を1つ増やす方が既存の分岐点（`switch t.State`）に素直に乗る

## 変えてよい前提 / 壊すと危ない前提

- **変えてよい**: `Until` を省略したときの既定（今日 +1ヶ月）、`until_reached` になったときの見た目の色、いつか区画の開閉の既定
- **壊すと危ない**: `Until` と `Due` を同じフィールドに統合しないこと。意味が逆なので、統合すると片方の表示が必ず誤作動する
- **壊すと危ない**: `someday` を `NeedsReason` の対象に入れないこと。棚上げは判断の記録ではなく置き場の変更で、対象に入れると `todo ask` が意味のない質問で埋まる
- **壊すと危ない**: `shelved` イベントの `Snapshot` を書き続けること。undo（ADR todo-0006）の復元経路がこれに依存している
