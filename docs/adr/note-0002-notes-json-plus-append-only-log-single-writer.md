# ADR note-0002: 保存は notes.json と追記専用 JSONL、書き手はサーバ 1 つ

## 背景

1 人用で件数は少ない（数百〜数千件）。DB は運用の手間に見合わない。
画面と CLI の両方から書くので、書き手が複数いると正本が二重化し、同時書き込みで壊れうる。

## 決定

- データディレクトリ（env `DATA_DIR`、既定 `~/.local/share/note-stock`）に次の 2 種を置く
  - `notes.json`: 現在の状態。一時ファイルに書いて rename で置き換える（途中の状態を読ませない）
  - `events-YYYY-MM.jsonl`: 操作ログ。追記専用で、月ごとに分ける。`add_note` / `delete_note` / `annotate` / `set_topic` / `add_topic`
- 書き手はサーバ 1 つ。サーバ内は mutex で直列化する
- CLI は HTTP API 経由でだけ読み書きする。サーバに届かなければ exit 1 で止まり、ファイルを直接書くフォールバックは持たない
- 現在の状態の書き込みに成功してからログを足す。状態の書き込みに失敗したら、メモリ上も古い状態のままにする
- ログは補助。追記に失敗しても状態の保存は成功として扱い、エラーログに残す（失敗を返すと呼び出し側が再試行して重複するため）
- 書き手が 1 つであることはデータディレクトリの `.lock` に対する排他ロック（flock）で強制する。同じディレクトリを別のサーバが開いていれば起動に失敗する

## 捨てた案

- **SQLite などの DB**: 件数が少なく、スキーマ変更とバックアップの手間のほうが大きい
- **CLI がファイルを直接書く**: サーバが同時に書くと競合する。書き手を 1 つにするほうが単純
- **JSONL だけにして毎回再生する**: 起動と一覧のたびに全ログを読み直す必要があり、削除や補足を反映するコードが増える

## 変えてよい前提 / 壊すと危ない前提

- **変えてよい**: ログの月次の区切り。`notes.json` の整形（インデント）。既定のデータの置き場
- **壊すと危ない**: 書き手をサーバ 1 つにする前提（CLI の直接書き込みを足すと rename による置き換えが競合する）。件数が少ない前提（全件を `notes.json` に持ち、一覧のたびに走査する）。件数が桁違いに増えるなら保存方式を見直す
