# ADR todo-0020: 親は長期に限らない。深さは 3 段まで、子の期限と着手順は親より前にする

## 背景

会議の準備タスクの期限が、会議の当日になっていた。準備は「会議で共有する」（期限は会議の日）の子として、それより前の期限で登録するべきだった。ADR todo-0019 では親になれるのが長期のタスクだけだったので、これが書けなかった。

## 決定

**親になれるのは、完了していないタスクすべて**（長期・着手順・待ち・いつか）。長期のタスクは引き続き子になれない。自分自身を親にする、ループを作る、完了済みのタスクを親にするのは断る。これは ADR todo-0019 の「親になれるのは長期のタスクだけ・1 段だけ」の部分を置き換える。長期を状態として帯に置く決定は変わらない。

**木は 3 段まで**（例: 長期 → 主たる行動 → 準備）。親を付けた結果、動かすタスク本人かその子孫のどれかが 4 段目になるなら断る。

**期限は子が親より厳密に前。** 両方に期限があるとき、子の期限が親と同じか後なら断る。確かめるのは、親付きで追加するとき（`AddChild`）、`SetParent`、子の `SetDue`、親の `SetDue`（直接の子のどれかが新しい期限以降になるとき）。期限を消すのは常に通す。完了済みのタスクは確認の対象から外す。

**着手順では、同じ帯（フォーカス中、またはそれ以外の着手順）の中で、子を親の上に置く。** 長期の親は着手順に居ないので、この規則は掛からない。

- `Reorder` と `FocusAt` で位置を指定した結果、子が親より下（親が子より上）になるなら、`ErrOrderRule` で断る（HTTP 409、`rule: true`）。画面はメッセージを出して元の並びに描き直す。位置を指定しないフォーカスのボタンは、断らず規則を満たす最も近い位置（親の直上、または最も下の子の直下）に置く
- 追加・親の変更・復帰では、利用者が手を掛けなくても規則が成り立つようにする。着手順の親の下に `AddChild` で足した子は、親の直上に入り、親の `Focused` を引き継ぐ。`SetParent` は、子が親より下なら親の直上へ動かす
- `renumber` が最後の砦になる。フォーカスの並べ直しのあと、同じ帯で親より下にいる open の子を親の直前へ移す。待ちからの復帰、完了の取り消し、フォーカスの解除はすべて `renumber` を通るので、ここで揃う

**undo。** `SetParent` が子を動かしたときは、イベントに動かす前の位置（`from_order`）を残し、undo は親を戻したうえで位置も戻す。`AddChild` の undo は追加の取り消しで、他のタスクの位置は `renumber` で元に詰まる。フォーカスのイベントは従来どおり位置を持つ。イベントの形は変えていないので、古いログはそのまま読める。

**画面。** 子の行には親の名前の先頭 6 文字を `↑` 付きで出す（超えたら `…`）。マウスを乗せると親までの経路（長期の親には「長期」を付ける）が出る。子を持つ行には破線の枠で `子 完了/全体` を出す。「子を追加」は完了していないすべてのタスクの行に出し、親の選択肢には長期と着手順のタスクを並べる（自分と子孫、深さを超える候補は除く）。API は全タスクに `parent_name` / `parent_path` / `kids_done` / `kids_open` を返す。

## 捨てた案

- **子を主たる行動の直下にまとめ、ブロックとして動かす**: 並べ替えが単純になるが、ほかの作業を子の間に挟めない。準備と準備の間に別件を置きたい場面は普通にある
- **主たる行動だけを別の帯に置く**: 主たる行動も手を動かす作業で、着手順に居るべきもの。帯を分けると、期限が近い順や並べ替えの対象から外れてしまう
- **子の期限が親と同じ日でも通す**: 今回の問題（準備が会議と同じ日になっていた）をそのまま許すことになる

## 変えてよい前提 / 壊すと危ない前提

- **変えてよい**: 段数の上限（`MaxDepth`）、タグの文字数、親の選択肢の並べ方
- **壊すと危ない**: `renumber` の最後の並べ直し。ここを外すと、復帰や undo のどれかの経路で子が親の下に残る
- **壊すと危ない**: `Reorder` / `FocusAt` が、断るときに状態を一切変えないこと。位置を動かしてから確かめるので、断る側で動かす前の状態へ戻している
